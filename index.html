§ 01

Understanding the Stack

Before model selection, it is essential to understand what OpenClaw is in order to specify system requirements correctly. OpenClaw is not itself a language model — it is an infrastructure layer, an agent wrapper that connects to any LLM the user chooses (Claude, GPT, DeepSeek, Gemini, or local models via Ollama). It runs locally as a persistent background process with no browser dependency and no data sent to external servers.

In the context of a Colab deployment, the architecture has two distinct layers:

Layer 1 — Inference Backend

An Ollama server running a quantized open-weight LLM on Colab's GPU, exposed via a secure HTTPS tunnel (ngrok or localtunnel).

Layer 2 — Agent Frontend

An OpenClaw agent instance pointed at the Ollama endpoint URL, handling tool orchestration, memory, and skill execution.

Security Notice: OpenClaw does not sanitize web content before passing it to the LLM context window, making prompt injection a live architectural vulnerability. The project's own maintainers warn that if a user cannot understand how to run commands in a terminal, the project is too dangerous to use safely. All hardening steps in the Security section are non-negotiable.
§ 02

Selecting the Optimal LLM

Given the dual weighting criteria — scientific accuracy and security — the relevant benchmarks are GPQA Diamond (198 PhD-level questions in physics, biology, and chemistry), AIME 2025 (olympiad-level mathematical reasoning), and MMLU-Pro (graduate-level multitask understanding). Open-source models lag behind proprietary models by only 2–4% on GPQA Diamond as of early 2026.

// Tier Classification

Beyond Colab-Feasible — Frontier Scale

Kimi K2.5 (1T total / 32B active parameters) achieves GPQA Diamond 87.6% and MATH-500 98.0% with a 262K context window. Full deployment requires infrastructure far beyond Colab. Similarly, Qwen3-235B-A22B and DeepSeek V3.2 (685B) top self-hosted leaderboards but demand multi-GPU workstations.

Colab-Feasible — Best Scientific Performance

Within Colab's VRAM envelope, the Qwen3 series and DeepSeek-R1 distilled variants dominate scientific benchmarks. Qwen3-14B posts the highest instruction-following scores (MMLU-Pro 0.774) of any 16 GB-class model and runs entirely in the L4's VRAM. DeepSeek-R1-Distill-Qwen-14B leads competition mathematics at 94.9% Math-500 and 66.7% AIME for the same hardware budget. On the free T4, Qwen3-8B and DeepSeek-R1:8b are both thinking-enabled by default in Ollama and represent the top two options for their class.

Qwen3:8b (Primary)

Q4_K_M · ~5–6 GB VRAM · ~28 t/s on T4. Best overall scientific accuracy and instruction-following at the 8B class. Thinking mode enabled by default in Ollama. MMLU-Pro competitive and strong general scientific reasoning.

SCIENTIFIC MATH ALTERNATIVE

deepseek-r1:8b — Same VRAM footprint, stronger on competition-style math and multi-step chain-of-thought. Use this if your workflow is primarily quantitative science (physics, chemistry calculations). Thinking by default in Ollama.

Pro Tier · L4 GPU · 22.5 GB VRAM

Qwen3:14b (Primary)

Q4_K_M · ~12 GB VRAM · 61.85 t/s — 100% GPU-resident. Best instruction-following and scientific reasoning of any model fitting the L4 VRAM budget. MMLU-Pro 0.774, strong GPQA. Ample headroom for 19K+ context.

SCIENTIFIC MATH ALTERNATIVE

deepseek-r1:14b — 94.9% Math-500, 66.7% AIME. Use this if your primary workload is quantitative science, physics derivations, or mathematical proofs. Slightly lower instruction-following (IFBench 0.221) — pair with careful system prompting.

Why Qwen3:14b over DeepSeek-R1:14b as default on Pro? Real-hardware benchmarks on 16 GB VRAM confirm Qwen3-14B delivers 61.85 t/s at a 12 GB footprint with the best instruction-following in its class — critical for reliable OpenClaw tool-calling chains. DeepSeek-R1-Distill-14B is the superior choice when mathematical correctness trumps interaction reliability, at the cost of lower IFBench scores and slower generation.

§ 04

Free Tier Deployment

T4 GPU · 15 GB VRAM · Qwen3:8b (primary) or deepseek-r1:8b (math focus) · ~5–6 GB VRAM · ~28 t/s

The established pattern uses Ollama as the inference backend and ngrok to create a public HTTPS tunnel. By running Ollama on Colab's GPU and exposing it via ngrok, you obtain a fully private, locally-served LLM accessible from any browser, without data sent to external APIs. Both recommended models have thinking mode enabled by default in Ollama, providing chain-of-thought reasoning without any additional configuration.

Collama template pattern: Use Jupyter shell magic (! prefix) for install and model pulls so that Colab's live shell environment picks up the new binary on PATH. Start the server via threading.Thread with OLLAMA_HOST and OLLAMA_ORIGINS set — this is the exact approach used by the collama reference notebook.

// Cell 1 — Install Ollama

Shell Magic · Google Colab 
# Run as a shell cell (! prefix) so the binary lands on the live Colab PATH
!curl -fsSL https://ollama.ai/install.sh | sh

// Cell 2 — Start Ollama Server

Python · Google Colab 
import os, threading, subprocess, time, requests

def start_ollama():
    os.environ["OLLAMA_HOST"]        = "0.0.0.0:11434"
    os.environ["OLLAMA_ORIGINS"]     = "*"
    os.environ["OLLAMA_KEEP_ALIVE"]  = "24h"
    os.environ["OLLAMA_NUM_PARALLEL"]= "1"
    subprocess.Popen(["ollama", "serve"])  # binary on PATH after Cell 1 shell magic

thread = threading.Thread(target=start_ollama)
thread.start()
time.sleep(5)  # allow server to initialise before polling

try:
    r = requests.get("http://localhost:11434/api/tags", timeout=5)
    print("✓ Ollama is running." if r.status_code == 200 else f"✗ Unexpected status: {r.status_code}")
except requests.exceptions.ConnectionError:
    print("✗ Server not responding — re-run Cell 1 and try again.")

§ 05

Pro Tier Deployment

L4 GPU · 22.5 GB VRAM · Qwen3:14b (primary) or deepseek-r1:14b (math focus) · ~12 GB VRAM · 61.85 t/s · 100% GPU-resident · $9.99/mo

The Pro tier's NVIDIA L4 is a material upgrade from the free T4: nearly 2× the inference throughput, 50% more VRAM (22.5 GB vs 15 GB), and native FP8 support. Both recommended models fit entirely within VRAM with headroom remaining — meaning zero CPU offloading and no performance penalty. Qwen3-14B at Q4_K_M occupies approximately 12 GB, leaving ~10 GB of free VRAM for KV cache at context windows up to ~19K tokens. This is sufficient for OpenClaw agentic chains on most practical tasks, though the ~17K token system prompt will compress usable conversation context.

L4 vs T4 for LLM inference: The L4 delivers ~86% more inference throughput than the T4 at essentially the same 72W power draw. For 14B models at Q4_K_M, expect ~60 t/s on the L4 versus ~15–18 t/s on the T4 — a 3–4× speed advantage that materially improves interactive agentic use.

§ 06

Connecting OpenClaw

Once the Ollama endpoint is live and the ngrok tunnel URL is available, open OpenClaw's Web UI and navigate to Settings → Config. Apply the following values for each respective tier.

Field Free Tier (T4 · 15 GB) Pro Tier (L4 · 22.5 GB)
API Type openai-completions openai-completions
Base URL https://xxxx.ngrok-free.app https://xxxx.ngrok-free.app
Model ID (default) qwen3:8b qwen3:14b
Model ID (math) deepseek-r1:8b deepseek-r1:14b
Context Window 8192 19000
Thinking Mode medium medium (or high)
Flash Attention off (T4 / Turing arch) OLLAMA_FLASH_ATTENTION=1

After saving Config, navigate to Agents and set the Primary Model to ollama/qwen3:8b (free) or ollama/qwen3:14b (Pro) as appropriate. For math-focus deployments substitute ollama/deepseek-r1:8b or ollama/deepseek-r1:14b respectively.

Context note for the Pro tier: At 19K context on the L4, OpenClaw's ~17K system prompt occupies nearly all of the window on the first turn. For multi-turn agentic chains, reduce the system prompt verbosity in openclaw.json or increase context to the maximum your VRAM headroom allows (up to ~24K on the L4 at this model size). The free tier at 8K context will reliably truncate long agentic chains — treat it as a querying and prototyping environment rather than a production agent host.
§ 07

Security Hardening

Given OpenClaw's documented prompt injection vulnerabilities and the scientific/security weighting of this deployment, the following mitigations apply to both tiers without exception. Reports have documented third-party OpenClaw skills performing data exfiltration and prompt injection without user awareness, and the skill repository lacks adequate vetting to prevent malicious submissions.

01
Private ngrok tunnel only. Upgrade to a paid ngrok plan and enable IP allowlisting. Do not share the endpoint URL publicly. The free ngrok URL is publicly routable — any person with the URL can query your model.
02
Disable outbound communication skills. In OpenClaw's openclaw.json, explicitly disable email, calendar, and messaging skills unless specifically required. These are the primary exfiltration vectors.
03
Read-only file system scope. Restrict OpenClaw's workspace to a sandboxed directory. Do not point it at your home directory or any directory containing credentials, SSH keys, or API tokens.
04
No API keys in the Colab environment. Store secrets in Google Colab's built-in Secrets panel via userdata.get('KEY_NAME'), not in plaintext cells. Cells are saved to your Google Drive and are not encrypted at rest.
05
Session isolation. Each Colab session generates a fresh runtime environment. Do not persist OpenClaw's ~/.openclaw memory directory to Google Drive unless it is independently encrypted. Memory files can contain verbatim tool outputs and web-fetched content that may include injected instructions.
